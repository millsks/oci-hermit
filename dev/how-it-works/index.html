    How it works¶

    This page describes what oci-hermit does today, and marks what is planned. The full design, including the parts not built yet, is in the design document.

    The short version¶

    Each oci-hermit run is one small virtual machine, started for that command and powered off when it ends:

    1. On the host, oci-hermit finds the image: a local OCI layout or .tar, else an image in its store, else it pulls the image from the registry. Every manifest, config and layer is checked against its sha256 digest.
    2. It turns each of the image's layers into a read-only EROFS disk, once per layer (later runs reuse them), works out the user to run as from the image's own /etc/passwd on those disks, and writes an initramfs with the guest agent as /init. Nothing is mounted on the host and nothing needs privileges. (An image run straight from a file has its files put in the initramfs under /rootfs instead.)
    3. It starts the bundled QEMU as a normal child process, with a software CPU (-accel tcg), no network device, and the layer disks attached read-only, and boots oci-hermit's own Linux kernel with that initramfs.
    4. In the guest, the agent runs as PID 1. It moves its root off the initramfs onto a tmpfs (so crun can pivot_root later), mounts /proc, /sys, the cgroup filesystem and /dev, says it is ready, and waits for instructions on a private serial channel.
    5. oci-hermit sends the command and the disks' serial numbers. The agent mounts each disk read-only and stacks them with overlayfs on /rootfs, under a writable layer in the guest's memory that is thrown away with the sandbox, so nothing the command writes reaches the disks. It writes an OCI runtime bundle for the command (its user, environment, working directory and terminal) and starts it in a container with crun: its own PID, mount, IPC, UTS, network and cgroup namespaces, Docker's default capabilities, a read-only /sys and only the usual devices. The agent relays the container's input, output and exit code.
    6. When the command exits, oci-hermit asks the agent to power off, and exits with the command's exit code.

    Components¶

    Part What it is
    Host tool oci-hermit, one Rust binary. The only process you start. It reads images, talks to registries, builds the initramfs and supervises QEMU.
    QEMU The bundled emulator (qemu/ in the package), started as a separate process. oci-hermit builds it itself, with only the two guest targets and no hypervisor accelerators, and refuses any other QEMU: its --version must be exactly 11.1.3 (oci-hermit-qemu-4) and it must offer the tcg accelerator. See Building QEMU.
    Guest kernel Linux 6.18 LTS, built by the project from tinyconfig plus a short list of options. x86_64 guests use QEMU's microvm machine; aarch64 guests use virt. See Building the guest.
    Guest agent hermit-agent, a static Rust binary that runs as PID 1. It never exits: on a shutdown request or any fatal error it syncs and powers the VM off.
    Container runtime crun 1.30, built statically by the project with json-c, libseccomp and libcap. The agent hands it an OCI runtime bundle per command.
    Control protocol Newline-delimited JSON over the virtio-serial port org.oci-hermit.control, at most 64 KiB a line. Version 1.4.

    What happens when you run¶

    The host side of this is split in two processes. run does the preparing, then starts the container's monitor, a background oci-hermit __monitor of its own (as Podman's conmon; there is no daemon). The monitor takes the container's running lock, starts QEMU (whose lifetime is tied to the monitor's), does the handshake, Run and Shutdown, appends the output to the container's log and records the exit code. run talks to it over a local channel, a Unix socket in the data folder that only you can open or a named pipe on Windows, in the same kind of JSON lines: it attaches, gets Booted, Started, the output and Exited, and sends your stdin. Without -d the monitor stops the sandbox if run goes away; with -d, run prints the container's ID after Started and returns, and logs reads the log while stop asks the monitor over the same channel to send the container's stop signal (Signal, protocol 1.6, which the agent passes on with crun kill) and to power the sandbox off if it has not ended in time. kill and Ctrl-C at a foreground run send Signal too. exec asks it to start another command in the container: the monitor sends the agent Exec (protocol 1.5) with a process number, the agent runs it with crun exec, and that command's input, output and exit code travel tagged with its number, to that exec alone.

    Isolation¶

    The security boundary is the emulator process. Guest code never runs directly on your CPU: QEMU translates every instruction, and the guest can touch only the devices QEMU gives it. The layers, outermost first:

    Layer Today Planned
    OS sandbox around QEMU None yet. QEMU runs as you, with your file access. seccomp and Landlock on Linux, App Sandbox on macOS, an AppContainer or low-integrity token on Windows (#38).
    Process lifetime QEMU ends when oci-hermit does: -run-with exit-with-parent=on on Linux and macOS, a kill-on-close Job Object on Windows.
    Software CPU TCG only. The bundle is built without KVM, HVF, WHPX or Xen, and any other QEMU is refused.
    Device model -nodefaults: one serial console and one virtio-serial port. No network card, disks, USB, display or sound. Read-only layer disks (#16), one restricted network card (#26), a file channel for bind mounts (#30).
    Network Sealed. No network device at all: no way out and no way in. libslirp with restrict=on (#26); -p bound to 127.0.0.1 only, even when 0.0.0.0 is asked for (#27); an egress test suite (#28).
    Control channel Anonymous pipes, no socket or file. Lines are capped at 64 KiB, anything that is not a message is refused, and every wait has a timeout: the host treats the guest as untrusted.
    Image input Every manifest, config and layer is checked against its sha256 digest when it is pulled, stored and read. Paths that climb out with .. are refused, device nodes are skipped. Signature verification with cosign or notation (#42).
    Inside the guest A crun container: its own PID, mount, IPC, UTS, network and cgroup namespaces (no user namespace), Docker's default capabilities and seccomp profile (unknown syscalls, and those needing capabilities it lacks, fail with EPERM), masked and read-only kernel paths, a device allow-list, run as the image's User (or -u). The VM stays the main boundary.
    Host code Rust, with unsafe code denied in the host crates; cargo deny checks advisories and licences; the QEMU and kernel sources are pinned by sha256. Code-signed Windows and macOS releases (#39).

    No network, on purpose¶

    The sandbox has no network device. A command that tries to reach anything fails:

    $ oci-hermit run public.ecr.aws/docker/library/alpine:3.20 wget -q -T 5 -O- http://example.com
wget: bad address 'example.com'

    Pulls happen in the host tool, so the guest never sees a registry, a credential or a route out. An image that downloads things when it starts fails here, which shows it is not self-contained. Published ports, bound to 127.0.0.1 only, are planned (#27); outbound access is not planned at all.

    The image store¶

    Pulled and loaded images live in one OCI image layout in your data folder (see Configuration). Blobs are shared between images and written only after their digest checks out. Each image is an entry in the layout's index.json, named by its full reference (docker.io/library/alpine:latest) and its platform; an image loaded without a name goes by its image ID.

    pull, load and run share the store and can run side by side. rmi and image prune delete blobs, so they need the store to themselves and refuse to start while another oci-hermit is reading it.

    The control protocol¶

    One JSON object per line, tagged by type. A different major version is refused; a newer minor version only adds messages or fields.

    {"type":"hello","version":[1,2]}
{"type":"run","argv":["sh"],"env":["PATH=/usr/bin:/bin","TERM=xterm-256color"],"cwd":"/","tty":true,"rows":40,"cols":120}
{"type":"output","stream":"stdout","data":"aGkK"}
{"type":"exited","code":0}
    Direction type Since Meaning
    host to agent hello 1.0 First message on the channel, with the host's protocol version.
    host to agent shutdown 1.0 Sync filesystems and power the guest off.
    host to agent run 1.1 Start one command: argv, env, cwd, tty, and the terminal's rows and cols. user (uid, gid, groups) since 1.2. One per session.
    host to agent stdin 1.1 Bytes for the command's stdin, base64, at most 16 KiB raw per message.
    host to agent stdin_closed 1.1 The host's stdin reached end of file.
    agent to host ready 1.0 Reply to a compatible hello.
    agent to host shutting_down 1.0 Reply to shutdown, before the power-off.
    agent to host error 1.0 A refused or failed message.
    agent to host started 1.1 The command started, with its PID.
    agent to host output 1.1 Output, base64, on stdout or stderr. With a terminal everything is stdout.
    agent to host exited 1.1 The exit status, or 128 plus the signal that killed the command.

    The host sends a user only to an agent that speaks 1.2 or later, because an older agent would ignore it and run the command as root. oci-hermit version prints the protocol version the host speaks.

    The QEMU command line¶

    Argument Why
    -accel tcg Software CPU emulation only. Never KVM, HVF, WHPX or Hyper-V.
    -nodefaults -no-user-config -display none -no-reboot The smallest device set, no host config files, no display. A guest reboot or panic ends QEMU.
    -machine microvm -cpu Haswell-v4,… x86_64 guests. The agent's static glibc needs an x86-64-v3 CPU; qemu64 would stop it with SIGILL.
    -machine virt -cpu max aarch64 guests.
    -m <MiB> -smp <cpus> Memory and CPUs: see Performance and limits.
    -run-with exit-with-parent=on Linux and macOS only. On Windows a Job Object does the same job.
    -chardev file,… -serial chardev:console The guest console goes to console.log, for people; oci-hermit never parses it.
    -chardev stdio,…,signal=off and a virtserialport named org.oci-hermit.control The control channel on QEMU's stdin and stdout. signal=off, so a byte is never taken as Ctrl-C.
    -append "console=ttyS0 panic=-1 tsc_early_khz=1000000" or "console=ttyAMA0 panic=-1" The kernel command line. The x86_64 guest's clock runs at a fixed 1 GHz on every host, and the kernel is told so.
    -drive …,readonly=on and -device virtio-blk-device,serial=layerN per layer The image's layer disks, read-only, found by the agent by serial number. No network device.
